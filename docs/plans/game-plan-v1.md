# 小布丁農場（little-pudding-game）— 實作計畫

> 寫成 2026-09-21（第二版：依使用者的遊戲設計重寫「遊戲設計」與相關工作包）。
> 路線已拍板：**A＝three.js 網頁 3D，先在 iPhone Safari 玩，後期用 Expo WebView 包成 App**。
> 執行採 checkpoint 制：每個 CP 有可判定的驗收，全過才進下一個；風險最高的先驗。

## Context

使用者要做一款「布丁農場」手機遊戲，畫面要有**動物森友會**那種圓潤、柔光、卡通著色的 3D 感（不是開放世界）。布丁模型用 **Blender MCP** 建。目標是**先自己在 iPhone 上玩**，不上架。

硬限制：**沒有 Mac**（Windows 11＋WSL2）。三路線比較已討論，使用者選 A（three.js 網頁 3D），理由：第一天就能在手機上看到 3D 櫥窗、Claude 能用 Playwright 自己截圖驗畫面、後段包 App 走已驗證過的 Expo→EAS→TestFlight 管線。

## 遊戲設計（使用者定稿，v1 範圍）

**畫面**：畫面中央是**一座直立玻璃落地櫃**（參考水族箱，直排三層；初始鏡頭 zoom in 讓它填滿畫面），**中層住布丁、上下兩層未解鎖**，每層右下角有名牌顯示狀態。兩側有**鄰櫃**延伸出畫面——v1 只是裝飾與上鎖外觀，之後才解鎖（見 D15、D17）。

**住客**：初期兩隻**普通黃色焦糖布丁**在櫥窗裡生活，**用彈跳移動**（自主行為，不是玩家拖曳）。

**原料浸泡盆（澡盆）**：櫥窗內一個小小精緻的澡盆。玩家要**消耗庫存**定期把它倒滿——「香醇濃郁的熱焦糖」或「冰鮮牛乳」二選一。

**布丁自主行為**：布丁在彈跳移動時，若發現自己「缺焦糖了」，會主動「啪嘰」一聲跳進澡盆，舒服地閉上眼睛泡澡。泡完澡會**產生甜點原料**，原料可以直接賣、或加工成甜點再賣。

**極端比例突變**：若一段時間內只灌牛奶、完全不給焦糖，黃色布丁會因牛奶過載身體**漸漸變白**，最後在一次**大彈跳**中永久突變成新物種【特濃鮮奶酪布丁】。

**染料／調風味澡盆**：用賣甜點的錢買特殊澡盆【宇治抹茶澡盆】【大湖草莓醬澡盆】；把普通黃色布丁放進去泡**幾天**，吸滿顏色與香氣後變異成【抹茶布丁】【草莓布丁】。

**兩條進程軸**（使用者補充）：
1. **自動化軸——「告別純手動，打造完全自動化的布丁生產線」**：一開始什麼都要手動（倒澡盆、撿原料、按加工、按賣），擋在前面的是**昂貴的自動化農場設備**，一台一台買齊後生產線全自動。
2. **經營軸——培育各種不同布丁，認真經營布丁甜點店**：物種越多、菜單越豐富，客人上門買甜點，收入比直接賣原料高。

### 純手動起點與自動化設備（v1 做 T1–T3，T4 留擴充）

| 手動動作（初期） | 對應設備 | 效果 | 定價原則 |
|---|---|---|---|
| 點澡盆 → 從庫存倒 1 份 | **T1 自動注液閥** | 澡盆低於 1 份就從庫存自動補 | 約 20 次泡澡的收入 |
| 泡完澡原料掉在櫥窗地板，玩家要**點一下才撿進庫存**（不撿會堆到 5 份上限、後續不再掉） | **T1 原料收集手** | 掉落即入庫 | 同上 |
| 點「加工」把 2 份原料做 1 份甜點 | **T2 甜點加工機** | 庫存夠就自動加工 | 約 60 次泡澡 |
| 點「賣」 | **T2 自動販售口** | 甜點做好自動賣（或留給客人，見經營軸） | 同上 |
| 點商店買焦糖／牛奶補貨 | **T3 補貨合約** | 庫存低於門檻自動買 | 約 150 次泡澡 |
| —— | T4 第二個櫥窗（擴充點，v1 不做） | 住客與澡盆翻倍 | —— |

設備是**櫥窗外的可見物件**（管線、機械手臂、小販售窗口），買了就出現在畫面上，看得到「生產線越來越完整」。

### 甜點店（經營軸；v1 做最小版，v1.5 擴充）

- v1：客人是**抽象的**——每隔一段時間出現一張「訂單卡」（要某物種的甜點 × 數量，出價＝直接賣的 2–3 倍，限時），有貨就成交。沒有對應物種就接不到那種訂單 → 這就是培育多物種的動機。
- v1.5（留擴充）：客人有模型走到販售窗口、店面等級、口碑。

### 轉成可實作的規則（數值是初版，放 `species.ts`／`balance.ts` 隨時調）

| 系統 | 規則 |
|---|---|
| 布丁狀態 | `species`（黃焦糖／鮮奶酪／抹茶／草莓）、`caramel`(0–100，每分鐘 −1)、`milkRatio`(近 N 次泡澡中牛奶占比，滑動窗)、`tint`(0–1，變白程度)、`flavorExposure`(對特殊澡盆的累積泡澡時數)、`mode`（`hopping`／`bathing`／`resting`） |
| 移動 | `hopping`：每 1.5–3 秒隨機選櫥窗地板內一點，拋物線跳過去，落地壓扁再回彈（squash & stretch） |
| 缺焦糖判定 | `caramel < 30` 且澡盆有液體且澡盆空位 → 下一次跳躍目標改為澡盆 → 落盆播「啪嘰」＋閉眼 → `bathing` 60 秒 |
| 泡澡結果 | 焦糖澡：`caramel` 回滿、產 1 份「焦糖原料」；牛奶澡：`caramel` 回 60、產 1 份「奶香原料」、`milkRatio` 窗推進；特殊澡盆：產對應原料、`flavorExposure` +1 小時 |
| 澡盆 | 容量 3 份液體；每次泡澡消耗 1 份；玩家從庫存倒入（焦糖／牛奶各自庫存；庫存用金幣補貨） |
| 極端突變 | `milkRatio ≥ 0.8` 連續 ≥ 5 次泡澡 → `tint` 每次泡澡 +0.25 → `tint ≥ 1` 後下一次落地改成「大彈跳」動畫 → `species = 鮮奶酪`，`tint` 歸零、`milkRatio` 清窗 |
| 風味突變 | 布丁在抹茶／草莓澡盆累積 `flavorExposure ≥ 48 小時`（遊戲時間，離線也算）→ 突變成對應物種 |
| 原料掉落 | 泡完澡在盆邊掉 1 份原料（`drops[]`，上限 5 份，滿了不再掉）；玩家點擊入庫，或由「原料收集手」自動入庫 |
| 經濟 | 原料可直接賣；加工：2 份同類原料 → 1 份甜點，售價 3 倍；訂單卡成交價＝甜點售價 × 2–3。金幣買：焦糖／牛奶補貨、特殊澡盆（一次性）、自動化設備 T1–T3（一次性） |
| 自動化 | 每台設備＝`state.equipment[zoneId]` 的一個布林（**每一區各買各的**，D45）；`sim.ts` 每 tick 依各區已裝設備自動執行對應手動動作（注液／收集逐區、加工／販售／補貨全場）；D49 起設備可以收進**全場共用的倉庫**再擺到別區（一台永遠只是一台，D45「每區各買各的」不變，多的只是搬家） |
| 家具與倉庫 | 澡盆＋五台設備＝家具（D49）。照一般手機經營遊戲的**擺放模式**：長按家具＝拿起來（或在倉庫卡點一件＝拿出來），畫面下方換成「收進倉庫／取消／確定」，可以反覆拖，**按確定才寫入**；紅圈（壓到別的家具或出界）時確定按不下去。倉庫卡**只列倉庫裡的東西**，一件一格（商品圖＋名字＋數量），點了就直接進擺放模式。澡盆收起來＝**盆裡液體直接倒掉**（先跳確認卡）、正在泡的布丁被請出來；一區可以沒有澡盆。注液閥掛在該區第一個澡盆上方、跟著盆走（拿起來只能收）；收集手掛頂板、可拖；布丁的落點避開所有落地家具 |
| 訂單卡 | 每 10–20 分鐘（遊戲時間）出一張，指定物種甜點 × 1–3、出價、限時 30 分鐘；從全部四物種抽，玩家沒有的物種那張只能過期——讓玩家看見「養新物種才接得到」 |
| 離線 | 以 `lastSeenAt` 補跑模擬，上限 8 小時（澡盆液體用完就停產；有自動化設備才會自動補） |
| 明確不做 | 帳號、雲端存檔、社交、IAP、推播、客人模型；**第二個櫥窗的「功能」v1 不實作，但外觀要做出來**（D15，2026-09-21 修訂） |

### 繁殖與配種（2026-09-22 使用者要求「過一段時間自動繁殖，不同布丁屬性培養出不同種類」）

**基因型**：每隻布丁帶兩個等位基因 `genes: [SpeciesId, SpeciesId]`（正規化排序，`[a,b]` 與 `[b,a]` 是同一個基因型）。等位基因只有四種基礎風味：`caramel`／`panna`／`matcha`／`strawberry`。

**表現型＝配種表**：純合（兩個等位基因相同）→ 該基礎物種；異合 → 該組合專屬的**混種物種**。四種等位基因兩兩配對共 6 對，因此 v1 共 **10 個物種**。

| 基因型 | 表現型 id | 暫定名（**待使用者簽核**） |
|---|---|---|
| caramel + caramel | `caramel` | 焦糖布丁（既有） |
| panna + panna | `panna` | 特濃鮮奶酪布丁（既有） |
| matcha + matcha | `matcha` | 宇治抹茶布丁（既有） |
| strawberry + strawberry | `strawberry` | 大湖草莓布丁（既有） |
| caramel + panna | `custard` | 卡士達布丁 |
| caramel + matcha | `hojicha` | 焙茶布丁 |
| caramel + strawberry | `brulee` | 草莓烤布蕾 |
| panna + matcha | `matchalatte` | 抹茶生乳布丁 |
| panna + strawberry | `berrymilk` | 草莓鮮乳布丁 |
| matcha + strawberry | `sakura` | 櫻花抹茶布丁 |

**遺傳**：子代各從雙親隨機取一個等位基因（孟德爾）。混種親代因此是「帶因者」：兩隻卡士達（caramel+panna）交配，子代 25% 純焦糖／50% 卡士達／25% 純鮮奶酪。

**環境影響配子**（把既有泡澡機制接進育種，這就是「不同屬性培養出不同種類」）：送出配子時，若該親代對某風味的 `flavorExposure` 已達門檻的一半，該配子有 `gameteShiftChance` 機率改成那個風味；`tint` 同理對應 `panna`。玩家倒什麼澡盆，就影響下一代的基因，不必等到親代自己突變完成。

**新生兒落點（溢出規則）**：優先跟雙親同區；雙親那一區滿了就落到**住客最少的已解鎖區**，全場都滿才停止繁殖。沒有這條規則繁殖會在第一隻之後整個停住（`npm run pacing` 實測：三小時只生一隻）——起始區生一隻就滿員，而每個新解鎖的區只送一隻住客、一隻湊不成一對。

**玩家對配種的直接操作**：`movePudding()`（搬家，規則層已完成、**UI 尚未接線**）。誰跟誰住同一區決定下一代的基因來源；配合 D30 的澡盆，玩家有兩個槓桿。

**繁殖觸發**（全自動，玩家只控制條件）：同一區內兩隻布丁，雙方 `caramel ≥ breedCaramelMin`、年齡 ≥ `matureAgeSec`、各自冷卻結束（`breedReadyAt`），且該區住客數 < `zoneCapacity` → 立刻產下一隻幼布丁（不做蛋、不用點擊，符合「自動繁殖」）。雙親各扣 `breedCaramelCost` 焦糖並進入冷卻——剛好在門檻上繁殖的話會直接跌破泡澡門檻，其餘情況也把下一次泡澡往前拉，繁殖因此接回既有的生產迴圈而不是外掛一條。

## 現況盤點

### 機器層／專案層盤點

2026-09-21 的機器層與專案層盤點（Apple 會籍與金鑰、本機工具鏈版本、內網限制、harness 記憶目錄）含本機與帳號資訊，留在私有記憶庫的 `STATE.md`，不進公開 repo。當時的結論摘要：Blender 與 uv 未裝（由 WP0-a 補裝）、目錄名底線／連字號的 slug 陷阱、內網擋 ngrok 所以 `expo start --tunnel` 不可用。

### 已查證的技術前提

- `@react-three/native`（Expo 原生即時 3D）官方標 pre-alpha「DO NOT USE YET」；expo-gl 版本衝突有真機崩潰紀錄 → 不用。
- Godot iOS 匯出官方要求 macOS＋Xcode → 不選。Unity Build Automation 免費 100 分鐘/月 Mac 編譯（2026-03 起）→ 一個月只能上手機 2–5 次 → 不選。
- **Blender MCP**（ahujasid，PyPI 已改名 `mcp-for-blender`，舊名仍可用）：`claude mcp add blender uvx mcp-for-blender`；需 Blender 3.0+、Python 3.10+、**uv 用官方安裝器**；內建 `export_scene`（GLB/FBX）、Poly Haven／Poly Pizza 免費素材、Hyper3D Rodin AI 生模（要額度）；**同時只能有一個 MCP client 連 Blender**。

## Checkpoint 與工作包

順序＝風險優先。**CP1 是整個計畫的最高風險驗證**（GLB 從 Blender 出得來、three.js 在 iPhone 跑得動），過了才投入規則與美術。

### CP0 環境：Blender MCP 接通（使用者要求另開任務做下載）

**WP0-a（使用者，真終端機／GUI）**
1. `winget install BlenderFoundation.Blender`（4.x）
2. `powershell -c "irm https://astral.sh/uv/install.ps1 | iex"` → 重開終端機，`uv --version`
3. 下載 `addon.py`（github.com/ahujasid/blender-mcp）→ Blender：Edit → Preferences → Add-ons → Install → 啟用 → 側欄 BlenderMCP → **Start MCP Server**

**WP0-b（主對話）**：專案寫 `.mcp.json`：
```json
{ "mcpServers": { "blender": { "command": "uvx", "args": ["mcp-for-blender"] } } }
```
（Windows 若 `uvx` 找不到，改 `"command":"cmd","args":["/c","uvx","mcp-for-blender"]`）。用專案層 `.mcp.json` 而非 `claude mcp add` 的 local scope——local 同名會靜默蓋過專案設定（全域記憶 pattern_mcp_scope_precedence）。

**驗收 CP0**：重啟 Claude Code 後呼叫 MCP `get_scene_info`，收到含 `objects` 的真實回應。負向對照：Blender 端按 Stop 再呼叫一次必須失敗。

### CP1 管線最高風險：一隻布丁從 Blender 到 iPhone

**WP1 repo 骨架＋hello scene（主對話）**：**第一步先把空目錄 `little_pudding_game` 改名 `little-pudding-game`**（對齊 harness slug；session cwd 隨之移動），再 `git init`、Vite+TS+three 骨架、`scene/{renderer,camera,lighting,cabinet}`（玻璃櫥窗依 D6，先用 BoxGeometry）、`debug/stats.ts`（fps、draw calls、`renderer.info.render.triangles` 寫進 `window.__lpg.stats`）、CLAUDE.md（不含機器路徑）、`.gitignore`。
**WP2 第一隻布丁（主對話驅動 Blender MCP，使用者視覺簽核）**：`execute_blender_code` 以 bpy 建圓角黃色焦糖布丁（底座圓柱＋上方壓扁球體＋焦糖頂＋兩點眼睛＋腮紅；眼睛做成獨立 mesh 以便閉眼切換），≤ 3k 面；`render_preview.py` 出 4 角度 PNG——**Claude 先自己 Read 圖迭代到自認可愛，再拿給使用者看**（使用者簽核不可省）；`export_scene` 出 `pudding_base.glb` → `optimize-models.mjs`。
**WP3 手機實測（主對話＋使用者）**：`npm run dev -- --host`＋手機熱點，使用者 iPhone Safari 開 `http://<PC IP>:5173/?debug=1` 讀 fps，截圖回傳；記錄 iPhone 型號、iOS 版本、低電量模式狀態進 STATE.md。

## 驗證方式（端到端）

1. 本機：`npm run dev -- --host` → 手機熱點下 iPhone 開 `http://<PC IP>:5173`。
2. 自動：`npm test`（vitest）、`npm run e2e`（Playwright，iPhone viewport，`--use-gl=angle --use-angle=swiftshader` 保證無頭 WebGL），截圖進 `tests/e2e/__screenshots__/`；用 `?fastTime=60`＋`?seed=` 讓「幾天」的流程幾秒內跑完。
3. 真機：CP1 用熱點網址、CP3 起用 GitHub Pages 網址，皆加 `?debug=1`；使用者回傳截圖即證據，存私有記憶庫 `evidence\`。
4. 完成宣告前逐條稽核：每個 AC 都要有本 session 的工具證據或使用者回傳的截圖；沒有就標「未驗」。

## 已知風險與對策

| 風險 | 對策 |
|---|---|
| Blender MCP 只能一個 client 連 | 只在本專案 `.mcp.json` 設；Claude Desktop 不設 |
| bpy 建模「可愛度」靠反覆調 | 每件先出 4 角度預覽，Claude 自讀迭代後再給使用者，不簽核不匯出；顏色類參數放 `species.ts` 可在 three.js 端微調不必回 Blender |
| 玻璃在手機上太貴 | D6：不用 transmission；AC1-3 若低於門檻先拿玻璃開刀 |
| 兩隻布丁同時要進澡盆 | 澡盆一次一隻；第二隻改為在盆邊等待（`resting`），邏輯層決定，測試覆蓋 |
| 突變／設備數值不好玩（太快／太慢、設備太貴或太便宜失去「告別手動」的成就感） | 全部常數集中 `balance.ts`；`?fastTime` 讓使用者幾分鐘體驗一輪再調；設備定價以「幾次泡澡的收入」為單位寫在設計表，調整時只動倍數 |
| 自動化全裝後遊戲沒事做 | 這是設計上的終點訊號：v1 到 T3 就停，T4 第二櫥窗與 v1.5 客人模型是下一階段的內容鉤子 |
| iOS Safari 低電量模式降頻 | AC1-3 量測時關低電量並記錄 |
| GitHub Pages 為公開 | D1 已標；要私有改 Cloudflare Pages |
| 三個月後要原生功能（推播、IAP） | WebView bridge（`postMessage`）；v1 不做 |
